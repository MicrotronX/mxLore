# Backlog Hygiene — fixed-pending-verify marker, auto-close, stale re-audit (SSoT)

Single source for the marker format, the deadlines and who runs what. Skills reference this file; they never restate the numbers.

Why: fixed items stayed `active` forever because closing was a separate manual step. The common case is "code built and released, only a test is still open" — other users and customers test it right after release, so waiting forever gains nothing.

## Marker (both parts required)
1. Tag `fixed-pending-verify` (`mx_add_tags`).
2. Content line, appended: `fixed-pending-verify since YYYY-MM-DD (<build/release>)` via `mx_update_doc(append_content=...)`.

- The deadline counts from the date in the **last** such line — NOT from `days_since_content_change`. A typo fix does not move the deadline; a new marker line restarts it.
- Tag without a parseable line → never auto-closed; reported by mxHealth P15.
- Regression before the deadline → remove the tag, or open a new bugreport that references the id.
- Applies to `bugreport`, `feature_request`, `todo`.

## Deadlines
`today_utc` = `date -u +%Y-%m-%d`, never the chat clock.
- `AUTO_CLOSE_DAYS = 14` (marker date <= today_utc - 14d).
- `STALE_DAYS = 30` (untagged active items, `days_since_content_change` > 30).
- `PLAN_AUDIT_DAYS = 14` (active plans/specs, `days_since_content_change` > 14 -> re-audit reads them).

## Auto-close — single locus: mxSave Step 3
The ONE place that writes. Runs in normal and `--loop` mode, no prompt (explicit, narrow exception to "never auto-archive FR/BR" — tagged items only).
1. `mx_search(project, tag='fixed-pending-verify', status='active', doc_type='bugreport,feature_request,todo', include_content=false, limit=50)`. ∅ → done.
2. `mx_batch_detail(doc_ids=[...], level='full')` (max 10/call) → take the last line matching `fixed-pending-verify since (\d{4}-\d{2}-\d{2})`.
3. Date <= today_utc - `AUTO_CLOSE_DAYS` → `mx_update_doc(doc_id, status='archived', append_content='auto-closed YYYY-MM-DD: <N>d after fixed-pending-verify without regression; regression -> new bugreport referencing this id', change_reason='auto-close fixed-pending-verify')`.
4. No parseable line → skip (no write).
Output: `Auto-closed: <N> (fixed-pending-verify >= 14d)` — silent if 0. MCP error → skip block, one warning line, never abort the save.

## Stale re-audit — mxHealth P15 (read-only) + mxSave count
- Candidates: `mx_search(project, doc_type='bugreport,feature_request,todo', status='active', include_content=false, limit=50)` MINUS the ids from the tag search above (client-side set difference; mx_search has no tag-exclusion filter).
- Stale = `days_since_content_change` > `STALE_DAYS`. Field missing (older server) → skip silently, never guess.
- Never auto-archived. mxHealth lists them and recommends a code re-audit (subagent, evidence `file:line` per item); the user decides.
- mxSave prints only `Stale open items: <M> (>30d) -> /mxHealth` — silent if 0.

## Setting the marker — mxSave FR/BR closure sweep
Per candidate: `archive` | `pending-verify` (apply both marker parts) | `keep`. No preselected option — the user picks per item (an FR can hold several asks; a plan task may cover only one).

## Plan/Spec -> FR/BR link (`implements`) — closes the gap when an item is built inside another plan
An FR/BR built by a plan/spec must not wait for a session to name its id. Server relation `implements` (existing type, no new one).
- **Link (mxPlan Step 2/3, mxSpec Section 2/3):** every `FR#`/`BR#`/`todo#` id named in the input or in `## Related` as source or co-implemented -> `mx_batch_detail` -> keep `doc_type in {feature_request, bugreport, todo}` -> `mx_add_relation(source_doc_id=<plan|spec>, target_doc_id=<item>, relation_type='implements')`. Server dedupes, re-run is safe. Tags (`spec-<id>` / `plan-<id>`) never create this relation: a tag says related, not implemented, and an `implements` relation would let Mark on archive close the item without a prompt. Tag-linked items surface only in the read-only done-in-plan list below. Output `Linked: <N> FR/BR (implements)` — silent if 0.
- **Mark on archive (mxPlan Step 4, mxSpec Step 4, right after the archiving `mx_update_doc` succeeded):** `mx_detail(<plan|spec>, max_content_tokens=1)` -> relations with `relation_type='implements'` AND `source_doc_id=<plan|spec>` -> `mx_batch_detail(target ids)` -> keep `doc_type in {feature_request, bugreport, todo}` AND `status='active'` AND tag `fixed-pending-verify` absent -> apply BOTH marker parts, line `fixed-pending-verify since YYYY-MM-DD (Plan#<id>)` / `(Spec#<id>)`. No prompt: the finished plan is the evidence, the 14-day window is the safety net. Output `Marked pending-verify: <N> FR/BR` — silent if 0. MCP error -> one warning line, never undo the archive.
- **Net (mxSave Step 3):** plans/specs archived in this session (tool returns) -> same mark rule, also in `--loop` mode. Catches archives done by hand (`mx_update_doc status='archived'`) outside the skills.

## Box close-out — ticking plan tasks / spec ACs (closes "built but never ticked")
A plan/spec archives only when every box is ticked (mxPlan Step 4, mxSpec Step 4, mxSave Step 3). Work built outside the plan step (ad-hoc workflow, bugfix, another plan) ticks nothing, so the doc stays active for good. Rule: a box is ticked when the work is finished, with evidence, by the session that built it; two nets catch the rest.
- **Box:** a line the doc type's own Step 4 counts — plan: the mxPlan Step 4 task regex (column zero, outside code fences); spec: the mxSpec Step 4 AC counting (under `## Acceptance Criteria`). A checkbox those rules do not count is not a box here. Only that first physical line is the box line; indented continuation lines belong to the box text but are never part of a match or a row.
- **Tick (the ONE write form, every caller, Main only):** the caller holds the doc body from `mx_detail(doc_id, max_content_tokens=0)` and copies the box line from it — never from a row, a summary or memory. `mx_update_doc(doc_id, replace_old='<EOL>- [ ] <rest of the box line><EOL>', replace_new='<EOL>- [x] <same rest><EOL>', change_reason='box close-out <caller>: <evidence>')` — `<EOL>` = the line break exactly as the body has it at that spot (LF or CRLF, bodies mix both); both breaks are part of the strings (the server matches a plain substring, so they stop `Add X` from matching inside `Add X and Y`); only the marker changes, the evidence lives in the revision's `change_reason`. One call per box, never a body rewrite. A box on the very first or last line of the body has no break on that side -> leave that `<EOL>` out of both strings. Exactly two repairs are allowed, each once, both copied from the body: "not found" -> the other break type (LF <-> CRLF); "more than once" -> append the verbatim next line to both strings. Still failing -> skip that box, print `<type>#<id>: box not tickable by rule - edit by hand: <box line>`, and drop it from the candidates. Never a guessed or reworded line.
- **Evidence:** `file:line` under the code root where the code does what the box text says. A box that asks for a test, a release, a user check or a rollout step is never a candidate from code presence, in any caller: it is ticked only when this session ran the step and saw the result (evidence = command + result) or the user states it is done. A hit in `*.md` never counts.
- **Confirm:** `AskUserQuestion`, multiSelect, up to 4 boxes per question, label `<type>#<id>: <box line, first 60 chars>`, description = the evidence, plus `last open box - the doc closes` when it is; not selected = stays open. No prompt possible (`--loop`, subagent, unattended) -> print the rows, tick nothing.
- **After ticking:** a doc left with zero open boxes -> run that doc type's own status transition now (mxPlan Step 4 / mxSpec Step 4, with their guards: open questions, dropped ACs, Mark on archive). Open boxes remain -> nothing.
- **Never blocks:** a declined prompt, an MCP error or a skipped box never stops the caller's own flow (workflow completion, save); one warning line at most.
- **Caller 1 — mxOrchestrate Workflow Completion (the moment the work is done):** candidates = active plans/specs whose id the workflow doc or this session named. None named -> `mx_search(project, doc_type='plan,spec', status='active', include_content=false, limit=4)`: <= 3 rows -> those; more -> print `box close-out skipped: <N> active plans/specs, none named` (the nets catch it). Per candidate read the body -> open boxes -> keep the ones fulfilled by files this workflow changed (source: the files this session edited plus the VCS status of the working tree; neither available -> 0 kept) -> Confirm -> Tick. 0 kept -> silent. Output `Ticked: <N> boxes (<type>#<id>, ...)`.
- **Caller 2 — mxSave stale sweep, mixed docs (net):** the sweep already has a per-box verdict. A doc with `divergence` boxes next to `confirmed_pending`/`unverifiable` ones is no longer dropped whole: its `divergence` boxes are tick candidates — but only a box whose verdict rests on a symbol the box itself names, found by the helper's Grep (evidence = that `file:line`). A verdict from path existence alone is doc-wide, not per box, and is never a candidate; test/release/rollout boxes are excluded per Evidence. All boxes `divergence` -> the existing archive prompt, unchanged. ⚡ The helper needs backtick-quoted paths in the doc; a doc without them is all `unverifiable` and only Caller 1 and Caller 3 reach it.
- **Caller 3 — Backlog re-audit rows `plan#`/`spec#` (net, below):** a row names the doc and the start of the box line; Main reads the body and takes the one open box line that starts with it (none or several -> skip + print).
- **Where Callers 2 and 3 run:** mxSave, in Main after the Step 3 subagent returned (same place as the FR/BR closure sweep) — the subagent only detects.
- **No box lines:** an active plan/spec with zero box lines can never close by rule. A caller that reads such a doc prints `<type>#<id>: no checkbox lines - cannot close by rule (/mxSpec or /mxPlan update)` once per run. Never turn prose into boxes silently.

## Backlog re-audit — mxOrchestrate resume (background, throttled, read-only)
Closes the gap for items built inside a plan that stays active for months: nobody names the id, so no closure path fires. The developer runs nothing extra: `resume` -> works -> `/mxSave`.
- **When:** right after `mx_session_start` succeeded in mxOrchestrate Init (the skill's resume path; hook text alone never spawns, lesson 2026-10-29) — once per session, never from the per-prompt hook ticks, never in `--loop`. The developer types nothing. Throttle: `mx_get_env(project, key='BACKLOG_REAUDIT_AT')` (⚡ always pass `key`) -> value missing or < `today_utc - REAUDIT_DAYS` (`REAUDIT_DAYS = 7`) -> run; else skip silently. ⚡ Only that `mx_get_env` result decides: a stamp quoted in handoff, session note, status.md or state is a claim, never the stamp (live 2026-10-29: handoff said "BACKLOG_REAUDIT_AT=2026-10-29", key did not exist, re-audit skipped; on retest the key was confirmed missing and the agent still skipped because "it already ran today"). Key missing = run, no judgment call, no exception. Never write the stamp value into handoff/notes.
- **Spawn (Main):** one background Agent, `model: sonnet`, no `name`, prompt = this section's "Agent contract" + project slug + code root (= the session's working directory; a different root only when CLAUDE.md names one) + the active ids: three searches, one per type (`mx_search(project, doc_type=<bugreport|feature_request|todo>, status='active', include_content=false, limit=50)`), so the 50-row cap applies per type (mx_search has no paging; one combined search left 5 of 55 mx-erp items unaudited on every run, 2026-10-29). A type hitting 50 rows -> the agent prints `re-audit list truncated: <type> at 50`. The throttle stamp is NOT written here: mxSave Step 3 writes it after the rows were offered (`mx_set_env(project, key='BACKLOG_REAUDIT_AT', env_value=<today_utc>)` — param is `env_value`), so rows lost to /clear before a save simply re-run on the next resume.
- **Second spawn, plans/specs (Main, same turn, only when due):** `mx_search(project, doc_type='plan,spec', status='active', include_content=false, limit=50)` -> keep rows with `days_since_content_change` > `PLAN_AUDIT_DAYS` (field missing -> skip, never guess); 50 rows returned -> print `plan/spec re-audit list truncated at 50`. This search is the due-check: its kept count decides whether a second agent is due (mxSave reads the same fact for the stamp). >= 1 kept -> a SECOND background Agent (`model: sonnet`, no `name`), prompt = "Plan/spec contract" below + slug + code root + those ids. Its own agent on purpose: one agent given items and plans together returned the items and dropped the plans (live 2026-11-24). 0 kept -> no spawn, silent.
- **Agent contract:** read-only, never writes MCP, never edits. Per item `mx_detail(doc_id=<id>, max_content_tokens=600)` -> derive 1-3 concrete probes from the ask (unit/file, function, route, setting key, UI string) -> Grep/Glob under the code root -> a hit that matches the ask = row `type#id — file:line — <what matched>`. No probe derivable -> count `not checkable`; probes present but nothing found -> no row (still open). Return max 20 lines: rows + one counts line `<N> likely done, <U> not checkable, <O> open, read <D>/<T>`. ⚡ Every item gets its `mx_detail` before it may be counted `not checkable`; a title-only verdict is invalid (live 2026-10-29: 50 of 70 judged by title). Batch the reads with `mx_batch_detail` (max 10 ids per call) if needed. No prose, no guesses: a row without `file:line` is invalid. A hit in skill/rule/doc text (`*.md`, SKILL.md, references/) only proves the rule is written: when the ask is that rule's behaviour or its proof, count `not checkable`, never a row.
- **Bugreport claim check (same agent, every bugreport):** a bugreport states a defect, so "a hit that matches the ask" never fires when the claim is wrong or outdated (5 such reports stayed active, 2026-11-24). Locate the code the report blames: unchanged -> no row (still open); visibly different -> row `bugreport#id — file:line — claim changed: <what the code does now>`; the report names no locatable code -> count `claim not locatable`. A `claim changed` row says the report no longer describes the code, not that the symptom is gone — the user decides. Counts line gains `, <C> claim changed, <L> claim not locatable`. More rows than the 20 lines hold -> last line `rows truncated at <N>`; never drop rows silently.
- **Plan/spec contract (second agent):** read-only, same bans. Per doc `mx_detail(doc_id, max_content_tokens=0)` -> box lines (regex = mxPlan Step 4). Per OPEN box derive 1-2 probes (header, function, setting key, column, route, message text) -> Grep/Glob under the code root -> the code does everything the box text names = row `<plan|spec>#id — <box line after the marker, first 60 chars or up to the line end, verbatim> — file:line — <what matched>`. Only the first physical line of a box is quoted; continuation lines are read for the meaning, never quoted. Same effect in a different form (a select option instead of a button) counts. Something the box names is missing (a setting that is read but changes no behaviour, half of an "A and B" box) -> no row, count `partial`. A box that asks for a test, release, user check or rollout -> never a row. Zero box lines -> line `<type>#id — no checkbox lines` (not a row, not counted). Return max 30 lines: rows first, then ONE counts line for all docs `<D> docs: <x> ticked, <o> open, <r> rows, <p> partial`. More rows than fit -> last line `rows truncated at <N>` (the rest re-runs next time); never drop rows silently. A row without `file:line` is invalid.
- **Main, when the result arrives:** print `Backlog re-audit: <N> likely done` + the rows (0 rows -> that one line only). These ids are closure-sweep candidates in mxSave Step 3 (source line there): archive / pending-verify / keep, no preselected option. Never auto-archive, never auto-mark. `claim changed` rows go into the same sweep with that wording as evidence. `plan#`/`spec#` rows print under `Plan/spec re-audit: <N> boxes built, not ticked` and are Box close-out candidates in mxSave Step 3 (Caller 3) — never ticked here.
